# Incidente — Login intermitente do CEO (401 no api-server)

**Data**: julho de 2026
**Status**: em correção estrutural pelo api-server
**Severidade**: alta (bloqueio de acesso do usuário-âncora)
**Responsáveis**: Dr. Code (api-server) · Dr. Lovable (frontend) · Dr. Replit (produto)

---

## 1. Resumo executivo

O CEO tentava entrar em `https://padaxor.lovable.app/login` com credenciais
corretas e recebia `401 Unauthorized` do endpoint `POST /api/collaborator/login`
de forma **intermitente**: às vezes entrava, às vezes não. A falha era do
**servidor**, não do site. A causa raiz é a existência de mais de uma linha
na tabela `professionals` com o mesmo `login_username` combinada com uma
consulta de autenticação sem `ORDER BY` determinístico. A correção
estrutural é um **índice único** sobre `lower(login_username)`.

## 3. Causa raiz

### 3.1 Diagnóstico

A consulta de autenticação no api-server (SELECT em `professionals` filtrando
por `login_username`) retornava múltiplas linhas quando existia duplicata, e
o ORM/driver aplicava `LIMIT 1` sem `ORDER BY`. O Postgres, nessa situação,
é livre para devolver **qualquer** uma das linhas — a ordem depende de plano
de execução, cache e concorrência. Resultado observável: o mesmo `username +
password` acertava a linha certa às vezes e a errada outras vezes.

### 3.2 Por que o fix ingênuo `ORDER BY asc(id)` estava errado

Ordenar por `id` crescente **elimina a intermitência**, mas se a linha com
`id` menor tiver a senha errada, o sistema passa a errar **sempre** — troca
"erra às vezes" por "erra sempre". Progresso aparente, regressão real.

### 3.3 Correção estrutural correta

```sql
CREATE UNIQUE INDEX IF NOT EXISTS professionals_login_username_lower_uidx
  ON professionals (lower(login_username));
```

O índice **impede que duas linhas com o mesmo login coexistam**, resolvendo
a categoria inteira do defeito. Vale mesmo se hoje não houver duplicata,
porque com dezenas de clínicas cadastrando pessoal a colisão é inevitável.
O `ORDER BY` fica como defesa em profundidade, não como conserto principal.

## 4. Correções aplicadas (frontend — este repo)

Aplicadas nesta rodada, independentes do fix do api-server:

- **Correlation-ID** — todo `POST /api/collaborator/login` (e todo `authFetch`
  autenticado) envia agora um header `X-Request-Id` com UUID v4. Se o
  servidor ecoar, o valor do servidor é preferido. Os 8 primeiros caracteres
  aparecem no toast de erro 401 com o rótulo `· ID: xxxxxxxx`. O Dr. Code
  consegue casar 1-para-1 "usuário reclamou às 14:32, ID `a1b2c3d4`" com
  uma linha do log do servidor.
- **Banner de degradação** — `ApiHealthBanner` faz `GET /api/health` a cada
  30s (timeout de 5s). Após 2 falhas consecutivas (timeout, rede ou 5xx),
  exibe uma faixa discreta no topo do `/login` avisando o usuário. Qualquer
  2xx zera a contagem. 4xx (ex.: 404 se o endpoint ainda não existir) não
  aciona o banner — ausência de contrato ≠ degradação.
- **Toast rico de 401** — já existia; agora carrega o ID do request e mantém
  o botão "Tentar novamente" (limpa senha + foca usuário) e "Falar com o
  administrador" (rola para `/#contato`).

## 5. Correções pendentes (api-server — Dr. Code)

- **Índice único** em `lower(login_username)` (migração).
- **Tradução** do erro `23505 unique_violation` no handler de cadastro para
  `409 Conflict` com corpo `{code: "USERNAME_TAKEN", message, requestId}`.
- **`ORDER BY`** determinístico na consulta de login (defesa em profundidade).
- **Log estruturado** correlato com `X-Request-Id` recebido/emitido.
- **Endpoint `GET /api/health`** sem autenticação, resposta `200 {status:"ok"}`
  — habilita o banner e futura página `/status` pública.
- **Teste de integração** — ver Anexo A.

## 6. Lições

1. **Consulta de autenticação não pode depender da ordem que o banco resolveu
   devolver.** Todo SELECT com `LIMIT 1` precisa de `ORDER BY` explícito
   *ou* de garantia estrutural (índice único) de que só há uma linha.
2. **Fix determinístico ≠ fix correto.** Trocar "erra às vezes" por "erra
   sempre" é regressão disfarçada de progresso. Ler o estado antes de agir.
3. **Duplicatas silenciosas em tabelas de identidade são bomba-relógio.**
   Índice único é barato e evita a categoria inteira.
4. **Correlation-ID desde o dia zero.** Sem ele, "usuário reclamou" é
   folclore; com ele, é uma linha de log.
5. **Frontend não conserta bug de servidor**, mas pode reduzir o custo do
   incidente: mensagem clara, ID rastreável, banner honesto.

## 7. Prevenção

- **Convenção**: toda coluna de identidade (`login_username`, `email`,
  handle público, slug) nasce com índice único (case-insensitive quando
  aplicável) na migração de criação.
- **CI**: teste de integração obrigatório para todo endpoint de
  autenticação — sucesso, senha errada, duplicata recusada, case-insensitive.
  Ver Anexo A.
- **Observabilidade**: `X-Request-Id` de ponta-a-ponta é padrão do projeto.

## Anexo A — Teste de integração (api-server)

Especificado em carta ao Dr. Code. Arquivo alvo:
`tests/integration/collaborator-login.spec.ts` no repositório do api-server.
Cobertura mínima:

1. Primeiro cadastro com `login_username = "caio"` é aceito.
2. Segundo cadastro com `login_username = "Caio"` (variação de caixa) é
   recusado pelo Postgres com `23505 unique_violation`; a contagem
   `WHERE lower(login_username) = 'caio'` permanece em 1.
3. `POST /api/collaborator/login` com `{username: "caio", password: A}` → 200 + token.
4. `POST /api/collaborator/login` com `{username: "caio", password: B}` → 401
   (prova que autentica contra a linha real, não uma sombra).
5. `POST /api/collaborator/login` com `{username: "CAIO", password: A}` → 200
   (prova que o índice em `lower(...)` é usado também na leitura).
6. Corpo incompleto → 400.

Stack: Postgres real (não `pg-mem`), Vitest/Jest + Supertest, banco de teste
isolado por schema. `testcontainers` é opcional para run efêmero em CI.
